# 🍎 کالری‌شمار (Calorie Counter Backend)

یک بک‌اند سبک برای دفترچهٔ غذا و شمارش کالری، نوشته‌شده با **FastAPI** و **SQLite**.

> کل پروژه در **یک فایل پایتون** (`main.py`) جمع شده است: موتور SQLAlchemy، مدل‌های ORM،
> مهاجرت‌ها، اپلیکیشن FastAPI و مجموعهٔ تست‌های خودکار. تنها فایل داده `food.db` است.

این سرویس به هر کاربر اجازه می‌دهد ثبت‌نام کند، پروفایلش را مدیریت کند، غذاها را جستجو کند و
وعده‌های غذایی‌اش (صبحانه، ناهار، شام، میان‌وعده) را با آرایه‌ای از غذاها ثبت یا کاملاً جایگزین کند.

## شروع سریع

```bash
# اجرا
python -m uvicorn main:app --reload
# یا
python main.py
```

سپس سرویس روی `http://127.0.0.1:8000` بالا می‌آید:

- مستندات تعاملی: `http://127.0.0.1:8000/docs`
- مستندات جایگزین: `http://127.0.0.1:8000/redoc`

**متغیرهای محیطی (اختیاری):**

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `JWT_SECRET` | `change-this-secret-before-public-use` | کلید امضای توکن. **در محیط واقعی حتماً تغییر دهید.** |
| `APP_TIMEZONE` | `Asia/Tehran` | منطقه‌زمانی محلی؛ برای تشخیص «امروز» وقتی تاریخ ارسال نشود. |
| `DATABASE_URL` | `sqlite:///<مسیر food.db>` | آدرس دیتابیس برای SQLAlchemy (برای تست یا جابه‌جایی دیتابیس). |

**نصب وابستگی‌ها:**

```bash
uv pip install -r requirements.txt
# یا
pip install -r requirements.txt
```

**اجرای تست‌ها:**

```bash
python main.py --selftest
```

مجموعهٔ تست داخل خود `main.py` است و روی یک کپی موقت از `food.db` اجرا می‌شود، پس دیتابیس
اصلی دست‌نخورده می‌ماند. در پایان اگر همه‌چیز درست باشد `ALL TESTS PASSED` چاپ می‌شود.

**استقرار روی سرور (فقط دو فایل):**

برای بردن پروژه روی سرور فقط به همین دو فایل نیاز دارید: `main.py` و `food.db`.

```bash
# ۱) وابستگی‌ها (یک‌بار)
pip install fastapi uvicorn sqlalchemy pydantic tzdata
# ۲) اجرا
python main.py
# یا: python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

- **سازگاری با دیتابیس قدیمی:** هنگام بالا آمدن، `init_db()` خودکار اجرا می‌شود و مهاجرت‌ها
  (ساخت جدول‌های غایب، افزودن `calories_cached`، تبدیل جدول قدیمی و ...) را به‌صورت
  **ایدمپوتنت** انجام می‌دهد. پس می‌توانید همان `food.db` قدیمی را ببرید؛ نیازی به اسکریپت
  جداگانه نیست و اجرای دوباره‌اش بی‌خطر است.
- **مسیر دیتابیس:** پیش‌فرض `food.db` کنار `main.py` است. اگر می‌خواهید جای دیگری باشد،
  `DATABASE_URL` را ست کنید (مثلاً `sqlite:////var/data/food.db`).
- **رمز توکن:** قبل از استفادهٔ عمومی حتماً `JWT_SECRET` را مقدار قوی بدهید.
- **فایل‌های اضافه:** پوشه‌های کش (`__pycache__/` و ...) خودکار ساخته می‌شوند و نیازی به
  بردن‌شان نیست.

## ساختار دیتابیس

فایل دیتابیس: `food.db` (SQLite). همهٔ دسترسی‌ها به دیتابیس از طریق **SQLAlchemy 2.0**
انجام می‌شود: موتور، مدل‌های ORM، reflection، مهاجرت‌ها و کوئری‌ها همه در `main.py` هستند.

**نقشهٔ فایل‌ها:**

| فایل | نقش |
|---|---|
| `main.py` | **کل پروژه** — موتور SQLAlchemy، مدل‌های ORM (`User`, `Meal`, `MealItem`)، reflection کاتالوگ `foods`، مهاجرت‌ها، اپلیکیشن FastAPI، تمام endpointها و تست‌های خودکار |
| `requirements.txt` | وابستگی‌های پروژه |
| `food.db` | تنها فایل داده (SQLite) |

```
┌────────────────────┐
│        users       │
│  (کاربران)         │
└─────────┬──────────┘
          │ 1
          │
          │ N
┌─────────▼──────────┐        ┌────────────────────┐
│        meals       │ 1    N │     meal_items     │
│  (سربرگ هر وعده)   ├────────►  (غذاهای هر وعده)  │
└────────────────────┘        └────────────────────┘

┌────────────────────┐
│        foods       │   (کاتالوگ مستقل؛ به کاربر وابسته نیست)
│  (کاتالوگ غذاها)   │
└────────────────────┘
```

### جدول `users` — کاربران

| ستون | نوع | توضیح |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | آیدی خودکار کاربر |
| `phone` | TEXT UNIQUE NOT NULL | شمارهٔ تلفن (یکتاست؛ نام کاربری) |
| `password_hash` | TEXT NOT NULL | هش رمز (PBKDF2-SHA256 با نمک) — رمز خام ذخیره نمی‌شود |
| `gender` | INTEGER NOT NULL CHECK(0,1) | جنسیت: `0` مرد، `1` زن |
| `height` | INTEGER NOT NULL | قد (سانتی‌متر) |
| `weight` | INTEGER NOT NULL | وزن (کیلوگرم) |
| `name` | TEXT NOT NULL | نام نمایشی |
| `birth_year` | INTEGER NOT NULL | سال تولد |

> ایندکس خودکار روی `phone` (به‌خاطر `UNIQUE`).

### جدول `foods` — کاتالوگ غذاها

این جدول از قبل داده و منبع ثابت غذاهاست و به هیچ کاربری وابسته نیست. ستون‌های `Food_Item` و
`Calories` همان ساختار دادهٔ اولیهٔ شما هستند.

| ستون | نوع | توضیح |
|---|---|---|
| `Food_Item` | TEXT | نام غذا |
| `Calories` | TEXT | کالری به‌صورت متن (لزوماً عدد خالص نیست؛ ممکن است «۳۰۰ تا ۵۰۰ کالری» یا `-` باشد) |
| `calories_cached` | REAL (NULLable) | مقدار عددیِ پارس‌شدهٔ کالری که هنگام اولین استفاده کش می‌شود |

> **آیدی غذا** در همهٔ endpointها همان `rowid` جدول است (چون جدول کلید اصلی عددی خودکار ندارد).
> این جدول با SQLAlchemy به‌صورت **reflection** خوانده می‌شود تا هم ساختار دادهٔ اصلی
> (`Food_Item`/`Calories`) و هم یک دیتابیس تازه‌ساخته (`name`/`calories`) پشتیبانی شود.

### جدول `meals` — سربرگ هر وعده

هر ردیف نمایندهٔ **یک وعده از یک کاربر، در یک روز، از یک نوع** است.

| ستون | نوع | توضیح |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | آیدی خودکار وعده |
| `user_id` | INTEGER NOT NULL → `users(id)` | صاحب وعده |
| `date` | TEXT NOT NULL | تاریخ روز ثبت، قالب `YYYY-MM-DD` |
| `meal_type` | INTEGER NOT NULL CHECK(1..4) | نوع وعده: `1` صبحانه، `2` ناهار، `3` شام، `4` میان‌وعده |
| `created_at` | TEXT NOT NULL | زمان اولین ساخت (ISO 8601 با آفست محلی) |
| `updated_at` | TEXT NOT NULL | زمان آخرین جایگزینی |
| — | **UNIQUE(`user_id`,`date`,`meal_type`)** | برای هر کاربر، هر روز، هر نوع وعده فقط یک رکورد |

### جدول `meal_items` — غذاهای هر وعده

هر ردیف نمایندهٔ **یک غذا داخل یک وعده** است (آرایهٔ `foods` در پاسخ‌ها از اینجا می‌آید).

| ستون | نوع | توضیح |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | آیدی خودکار آیتم |
| `meal_id` | INTEGER NOT NULL → `meals(id)` ON DELETE CASCADE | وعدهٔ والد |
| `food_id` | INTEGER NOT NULL | آیدی غذا؛ `0` یعنی «غذای دلخواه» (خارج از کاتالوگ) |
| `food_name` | TEXT NOT NULL | نام غذا (از کاتالوگ یا دلخواه) |
| `calories` | REAL NOT NULL | کالری هر واحد |
| `amount` | REAL NOT NULL | مقدار مصرفی |
| `unit` | TEXT NOT NULL | واحد؛ برای غذای کاتالوگ همیشه `serving` |

> ایندکس `idx_meal_items_meal_id` برای جستجوی سریع آیتم‌های یک وعده. حذف یک وعده،
> آیتم‌هایش را هم کاسکید پاک می‌کند.

### جدول `sqlite_sequence`

جدول داخلی SQLite برای پیگیری `AUTOINCREMENT`. (دست نزنید.)

## مفاهیم کلیدی

- **کلید یکتای وعده = `user_id` + `date` + `meal_type`.**
  برای همین، هر بار که `POST /meals` می‌زنید، **کل وعدهٔ همان روز/همان نوع جایگزین می‌شود**
  (نه اینکه به قبلی اضافه شود). آیتم‌های قبلی حذف و آرایهٔ جدید درج می‌شود.
- **`food_id = 0`** یعنی غذای دلخواه؛ در این حالت باید `name`، `calories` و `unit` را خودتان بفرستید.
- **غذای کاتالوگ:** فقط `food_id` و `amount` کافی است؛ نام و کالری از جدول `foods` خوانده می‌شود.
  مقدار `unit` همیشه `serving` می‌شود.
- **`total_calories`** در پاسخ = `Σ (calories × amount)`.
- **تاریخ پیش‌فرض:** اگر `date` را نفرستید، «امروز» بر اساس `APP_TIMEZONE` در نظر گرفته می‌شود.
- **احراز هویت:** توکن Bearer (شبیه JWT). همهٔ endpointها به‌جز ثبت‌نام/ورود و کاتالوگ غذا،
  توکن لازم دارند و فقط دادهٔ خودِ کاربر را برمی‌گردانند.

## احراز هویت

پس از `register` یا `login` یک `access_token` می‌گیرید. آن را در هدر همهٔ درخواست‌های محافظت‌شده بگذارید:

```
Authorization: Bearer <access_token>
```

عمر توکن **۳۰ روز** است. اگر توکن نباشد یا نامعتبر/منقضی باشد → `401`.
اگر توکن معتبر باشد ولی کاربرش دیگر وجود نداشته باشد، همهٔ endpointهای محافظت‌شده `401`
برمی‌گردانند (`کاربر این توکن دیگر وجود ندارد`).

## مرجع Endpointها

### 1) `POST /auth/register`

ساخت حساب جدید. خروجی: توکن.

**بدنه:**
```json
{
  "phone": "09120001122",
  "password": "secret123",
  "gender": 0,
  "height": 178,
  "weight": 74,
  "name": "علی",
  "birth_year": 1994
}
```
محدودیت‌ها: `gender` فقط ۰ یا ۱؛ `height` بین ۱ تا ۳۰۰؛ `weight` بین ۱ تا ۷۰۰؛
`birth_year` بین ۱۹۰۱ تا سال جاری؛ `phone` حداکثر ۳۲ کاراکتر؛ `password` بین ۱ تا ۲۵۶ کاراکتر؛
`name` حداکثر ۱۰۰ کاراکتر.

**پاسخ `201`:**
```json
{ "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9....", "token_type": "bearer" }
```

**خطاها:** `409` اگر شماره تکراری باشد، `422` اگر داده نامعتبر باشد.

---

### 2) `POST /auth/login`

ورود با شمارهٔ تلفن و رمز.

**بدنه:**
```json
{ "phone": "09120001122", "password": "secret123" }
```

**محدودیت‌ها:** `phone` حداکثر ۳۲ کاراکتر، `password` حداکثر ۲۵۶ کاراکتر.

**پاسخ `200`:** همان شکل ثبت‌نام (توکن).

**خطا:** `401` اگر شماره یا رمز اشتباه باشد.

---

### 3) `GET /me`

اطلاعات کاربر لاگین‌شده. **نیاز به توکن.**

**پاسخ `200`:**
```json
{
  "id": 4,
  "phone": "09120001122",
  "name": "علی",
  "gender": 0,
  "height": 178,
  "weight": 74,
  "birth_year": 1994
}
```

### 4) `PATCH /profile`

به‌روزرسانی جزئی پروفایل. فقط فیلدهایی که می‌فرستید تغییر می‌کنند. **نیاز به توکن.**

**بدنه (هر زیرمجموعه‌ای):**
```json
{ "height": 179, "weight": 75, "age": 30 }
```
> اگر `age` بفرستید، خودکار به `birth_year` تبدیل می‌شود (`سال جاری − age`).

**محدودیت‌ها:** `height` بین ۱ تا ۳۰۰، `weight` بین ۱ تا ۷۰۰، `age` بین ۱ تا ۱۳۰.

**پاسخ `200`:** شیء کامل کاربر (مانند `GET /me`).

**خطا:** `400` اگر هیچ فیلدی نفرستید.

---

### 5) `GET /foods`

فهرست صفحه‌بندی‌شدهٔ کاتالوگ غذاها. (بدون توکن)

**پارامترهای کوئری:** `limit` (۱..۱۰۰۰، پیش‌فرض ۱۰۰)، `offset` (≥۰، پیش‌فرض ۰).

**پاسخ `200`:**
```json
[
  { "id": 1, "name": "سیب", "calories": "52" },
  { "id": 2, "name": "موز", "calories": "89" }
]
```
> دقت کنید `calories` اینجا **رشته** است (همان مقدار خام کاتالوگ).

---

### 6) `GET /foods/search`

جستجوی غذا بر اساس **نام** (کامل/جزئی) یا **آیدی عددی**. (بدون توکن)

**پارامتر:** `q` (حداقل ۱ و حداکثر ۱۰۰ کاراکتر).

```http
GET /foods/search?q=سیب
GET /foods/search?q=1          # جستجو بر اساس آیدی
GET /foods/search?q=۱          # حتی با ارقام فارسی
```

**پاسخ `200`:** آرایه‌ای از غذاها (حداکثر ۱۰۰ مورد):
```json
[ { "id": 1, "name": "سیب", "calories": "52" } ]
```

### 7) `POST /meals` (مهم‌ترین endpoint)

**ساخت یا جایگزینی کامل** یک وعده (بر اساس کاربر + تاریخ + نوع). **نیاز به توکن.**

**بدنه:**
```json
{
  "meal_id": 1,
  "date": "2026-10-25",
  "foods": [
    { "food_id": 1, "amount": 2 },
    { "food_id": 0, "amount": 1, "name": "کیک خانگی", "calories": 350, "unit": "برش" }
  ]
}
```

**فیلدها:**

| فیلد | اجباری؟ | توضیح |
|---|---|---|
| `meal_id` | ✅ | `1` صبحانه، `2` ناهار، `3` شام، `4` میان‌وعده |
| `date` | ❌ | `YYYY-MM-DD`؛ پیش‌فرض «امروز» در `APP_TIMEZONE`؛ بازهٔ مجاز ۱۹۰۰-۰۱-۰۱ تا ۲۱۰۰-۱۲-۳۱ |
| `foods` | ✅ | آرایه، حداقل ۱ و حداکثر ۱۰۰ آیتم |
| `foods[].food_id` | ✅ | آیدی غذا از کاتالوگ، یا `0` برای دلخواه |
| `foods[].amount` | ✅ | عدد بزرگ‌تر از ۰ و حداکثر ۱۰۰٬۰۰۰ |
| `foods[].name` | برای دلخواه ✅ | نام غذا (حداکثر ۱۰۰ کاراکتر) |
| `foods[].calories` | برای دلخواه ✅ | کالری هر واحد (۰ تا ۱۰۰٬۰۰۰) |
| `foods[].unit` | برای دلخواه ✅ | واحد (مثلاً «عدد»، «گرم») — حداکثر ۳۲ کاراکتر |

**پاسخ `201` (وعدهٔ جدید ساخته شد):**
```json
{
  "id": 5,
  "user_id": 4,
  "date": "2026-10-25",
  "meal_id": 1,
  "meal_name": "breakfast",
  "foods": [
    { "id": 5, "meal_id": 5, "food_id": 1, "food_name": "سیب", "calories": 52.0, "amount": 2.0, "unit": "serving" },
    { "id": 6, "meal_id": 5, "food_id": 0, "food_name": "کیک خانگی", "calories": 350.0, "amount": 1.0, "unit": "برش" }
  ],
  "created_at": "2026-10-25T17:52:58.548975+03:30",
  "updated_at": "2026-10-25T17:52:58.548975+03:30",
  "total_calories": 454.0
}
```

**پاسخ `200` (وعدهٔ موجود جایگزین شد):** همان شکل، ولی `id` و `created_at` ثابت می‌مانند،
`updated_at` به‌روز می‌شود و `foods` دقیقاً آرایهٔ جدید است.

> **رفتار اتمیک:** تمام غذاها اول اعتبارسنجی می‌شوند؛ اگر یکی نامعتبر باشد، **هیچ تغییری در
> دیتابیس رخ نمی‌دهد** و وعدهٔ قبلی دست‌نخورده می‌ماند.

**خطاها:** `401`، `404` (غذای ناموجود)، `422` (اعتبارسنجی/کالری نامعتبر/محدودهٔ خارج).

### 8) `GET /meals`

دریافت وعده‌های کاربر. **نیاز به توکن.**

- `GET /meals?day=2026-10-25` → فقط وعده‌های همان روز (مرتب بر اساس `meal_type`).
- `GET /meals` → همهٔ وعده‌ها در همهٔ روزها (مرتب بر اساس `date` سپس `meal_type`؛ `date` در پاسخ `null`).

**پاسخ `200`:**
```json
{
  "date": "2026-10-25",
  "meals": [
    {
      "id": 5, "user_id": 4, "date": "2026-10-25", "meal_id": 1, "meal_name": "breakfast",
      "foods": [ { "id": 7, "food_id": 0, "food_name": "تخم مرغ", "calories": 155.0, "amount": 2.0, "unit": "عدد" } ],
      "created_at": "2026-10-25T17:52:58.548975+03:30",
      "updated_at": "2026-10-25T17:52:58.564963+03:30",
      "total_calories": 310.0
    }
  ]
}
```

## سناریوهای کامل قدم‌به‌قدم

### سناریو ۱ — ثبت‌نام، ورود و دیدن پروفایل

```http
POST /auth/register
```

### سناریو ۲ — جستجوی غذا و گرفتن آیدی

```http
GET /foods/search?q=سیب
# → [ { "id":1, "name":"سیب", "calories":"52" }, ... ]
```

### سناریو ۳ — ثبت اولین صبحانه (سیب + کیک دلخواه)

```http
POST /meals
Authorization: Bearer <token>
{ "meal_id":1, "date":"2026-10-25",
  "foods":[ {"food_id":1,"amount":2}, {"food_id":0,"amount":1,"name":"کیک خانگی","calories":350,"unit":"برش"} ] }
# → 201، دو آیتم، total_calories = 2×52 + 1×350 = 454
```

### سناریو ۴ — تغییر همان صبحانه (جایگزینی کامل) ⭐

```http
POST /meals
Authorization: Bearer <token>
{ "meal_id":1, "date":"2026-10-25",
  "foods":[ {"food_id":0,"amount":2,"name":"تخم مرغ","calories":155,"unit":"عدد"},
            {"food_id":0,"amount":1,"name":"شیر","calories":120,"unit":"لیوان"} ] }
# → 200، همان id؛ کیک حذف و تخم‌مرغ+شیر جایگزین شد. created_at ثابت، updated_at به‌روز.
```

### سناریو ۵ — ثبت ناهار برای امروز (بدون فرستادن تاریخ)

```http
POST /meals
Authorization: Bearer <token>
{ "meal_id":2, "foods":[ {"food_id":9,"amount":1} ] }
# → 201، date = امروز به وقت Asia/Tehran
```

### سناریو ۶ — دیدن وعده‌های امروز

```http
GET /meals?day=2026-10-25
Authorization: Bearer <token>
# → 200، آرایهٔ وعده‌ها شامل صبحانه و ناهار
```

### سناریو ۷ — کوچک/بزرگ شدن آرایه

هر بار که پست می‌زنید، تعداد آیتم‌های ذخیره‌شده **دقیقاً** برابر آرایهٔ ارسالی است:
۱ آیتم → ۳ آیتم → ۱ آیتم. (`meal_id` ثابت می‌ماند.)

### سناریو ۸ — غذا با کالری متنی در کاتالوگ

```http
POST /meals
Authorization: Bearer <token>
{ "meal_id":3, "date":"2026-10-25", "foods":[ {"food_id":1243,"amount":1} ] }
# food 1243 = "باقلوا" با کالری "450 تا 500 کالری"
# → 201، calories = 475.0 (میانگین بازه)
```
اگر غذایی هیچ عددی نداشته باشد (مثل «گلاب» با `-`) → `422`.

### سناریو ۹ — جداسازی کاربران و روزها

- دو کاربر مختلف با همان `meal_id` و همان روز، دو وعدهٔ مستقل دارند.
- یک کاربر با همان `meal_id` ولی `date` متفاوت، وعده‌های مستقل دارد.
- هرگز رکورد تکراری ساخته نمی‌شود (کلید یکتا تضمین می‌کند).

## کدهای خطا

| کد | معنا | نمونه |
|---|---|---|
| `400` | درخواست نامعتبر | `PATCH /profile` بدون هیچ فیلد |
| `401` | توکن لازم/نامعتبر/منقضی/کاربر حذف‌شده | نبود هدر `Authorization`، یا توکن کاربری که دیگر وجود ندارد |
| `404` | پیدا نشد | `food_id` ناموجود در کاتالوگ، یا پروفایل کاربر حذف‌شده |
| `409` | تضاد | شمارهٔ تلفن تکراری در ثبت‌نام |
| `422` | اعتبارسنجی | نوع/محدودهٔ نامعتبر، آرایهٔ خالی یا بیش از ۱۰۰ آیتم، رشتهٔ بیش از حد بلند، تاریخ خارج از بازه، کالری متنی نامعتبر |

فرمت خطای اعتبارسنجی (Pydantic):
```json
{ "detail": [ { "type": "greater_than", "loc": ["body","foods",0,"amount"], "msg": "Input should be greater than 0", "input": 0 } ] }
```
فرمت خطای منطقی (HTTPException):
```json
{ "detail": "غذا پیدا نشد" }
```

## نکات فنی و محدودیت‌ها

- **تک‌فایلی:** کل کد در `main.py` است (موتور، مدل‌ها، مهاجرت‌ها، endpointها و تست‌ها)؛
  تنها فایل داده `food.db` است. برای بازاجرای تست‌ها: `python main.py --selftest`.

- **لایهٔ داده (SQLAlchemy):** تمام دسترسی‌ها از طریق SQLAlchemy 2.0 انجام می‌شود. مدل‌های
  `User`, `Meal`, `MealItem` به‌صورت ORM تعریف شده‌اند؛ جدول کاتالوگ `foods` به‌خاطر ساختار
  دادهٔ اولیه (کلید عددی خودکار ندارد و نام ستون‌هایش متفاوت است) با reflection و کوئری‌های
  Core خوانده می‌شود و `rowid` به‌عنوان آیدی غذا استفاده می‌گردد. upsert وعده با
  `INSERT ... ON CONFLICT ... RETURNING` انجام می‌شود تا نوشتن‌های همزمان امن باشند.
- **جایگزینی آرایه‌ای، نه ادغام:** `POST /meals` همیشه کل وعده را بازنویسی می‌کند. اگر رفتار
  «افزودن به قبلی» لازم دارید، باید endpoint جدا یا پارامتر `mode` اضافه شود.
- **`GET /foods` و `/foods/search`** کالری را **رشتهٔ خام** برمی‌گردانند؛ تبدیل عددی فقط داخل
  منطق وعده انجام می‌شود (`calories_cached`).
- **محدودیت مقادیر و رشته‌ها:** `amount` و `calories` هر کدام حداکثر `100,000` (`MAX_AMOUNT`,
  `MAX_CALORIES`)؛ `foods` حداکثر `100` آیتم (`MAX_FOODS_PER_MEAL`)؛ `name`≤۱۰۰، `unit`≤۳۲،
  `phone`≤۳۲، `password`≤۲۵۶ کاراکتر؛ `height`≤۳۰۰ و `weight`≤۷۰۰. ورودی خارج از این بازه‌ها
  `422` می‌گیرد.
- **بازهٔ تاریخ:** `date` باید بین `1900-01-01` و `2100-12-31` باشد (مقادیری مثل `9999-12-31`
  رد می‌شوند).
- **رکورد کاربر حذف‌شده:** هر endpoint که کاربر را لازم دارد، پس از اعتبارسنجی توکن وجود واقعی
  کاربر را هم چک می‌کند؛ اگر کاربر حذف شده باشد `401` برمی‌گردد (نه خطای سرور).
- **زمان:** زمان‌ها با آفست محلی (`APP_TIMEZONE`) ذخیره و برگردانده می‌شوند.
- **محدودیت‌های کاتالوگ:** برخی ردیف‌های `foods` کالری متنی یا `-` دارند؛ این‌ها هنگام ثبت وعده
  ممکن است `422` بدهند (طبیعی است، داده منبع معتبر نیست).
- **نبود endpoint حذف:** الان امکان حذف کل یک وعده یا یک آیتم از طریق API وجود ندارد
  (جایگزینی آرایه‌ای تا حدی این کار را می‌کند).
- **`JWT_SECRET`:** پیش‌فرض ناامن است؛ در محیط واقعی حتماً مقدار قوی ست کنید.
